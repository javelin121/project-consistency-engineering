# 老仓库怎么迁移

老仓库的规矩只有一条：**先看，后说，最后才动手。** 没被确认的东西一个字节都不改。

## 五步

1. **审计**（只读）
   `pce audit`。报告五块：仓库多大、根目录长什么样、层级现状、明显的坏味道、入口文件多少行。它只报现状，不给方案。

2. **找归档区**
   扫 `archive/`、`_archive/`、`old/`、`deprecated/`、`legacy/`，找到就问“是这个吗”；一个都没有就问“建不建”。

3. **出方案**（agent 的活）
   按审计结果写一份迁移建议：哪些目录成为分区、哪些文件挪走、哪些进归档、哪些引用要改。一条一条列，别打包成“重构一下”。

4. **逐条确认**
   人点头一条做一条。删除、移动逐个确认；新建文件可以整批。先做只增不减的那部分（补导航、补契约），再做移动。

5. **复查**
   每步之后 `pce check`。结束时应当零 error；`git status` 要能看出每一步改了什么。

## 老仓库的三个现实

- **可能不是 git 仓库**：`map` 的“最后更新”那一列会空着，其余照常。先问要不要 `git init`。
- **可能已经有自己的导航**：先认它，把格式改成四列，别推翻重写。
- **可能有没人敢删的历史包袱**：先归进归档区，不删。归档只进不出。

## 别这样迁移

- 一次性 `git mv` 全仓重排：出了问题回不去，引用也改不完。
- 先改文件再补契约：契约就成了事后追认，不再是判定依据。
- 把 `audit` 的“坏味道”直接当待办：它只是现象，方案要人判断。
