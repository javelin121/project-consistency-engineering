# 为什么仓库会烂，以及五条底线

## 它烂在五个时刻，不是烂在一次大事故

| 时候 | 发生了什么 | 后果 |
|---|---|---|
| 开工第一天 | 没人定过哪些文件能直接放根上 | 根目录慢慢变成杂物间 |
| 长到第二个月 | 新目录一个接一个建，没人说得清各管什么 | 想找东西只能问人 |
| 中期 | 文件挪了位置，引用它的文档和代码没跟上 | 点开链接是空的，import 报错 |
| 几个人同时干活 | 每个 agent 各建一套，名字还不一样 | 两份东西干同一件事 |
| 换人接手 | 上一轮的结构只活在上一轮脑子里 | 新人得先挨个问人，再自己读半天 |

真正的根因只有一句：**没有任何一处写下来“这个文件为什么在这里”，也没有一条命令能查出它不在该在的地方。**

## 五条底线

底线是“态度”，不是“动作”：人会不会犯错是概率问题，底线是错了也逃不掉。

| 编号 | 底线 | 大白话 |
|---|---|---|
| I1 归属完备 | 每个文件都能被一条规则解释“为什么在这里” | 要么在某个分区里，要么在根白名单里；没有“先放这儿再说” |
| I2 地图完备 | 每个目录都能在导航里找到“它负责什么” | 有子目录的目录必须有一份 `navigation.md`；叶子不用 |
| I3 时效可查 | 每层导航都能看出“这一层多久没动过” | 靠 git 时间自动填，不手写、不进检查 |
| I4 名实相符 | 名字和引用都对应真实存在的东西 | 没有幽灵文件：链接不能指向不存在的文件 |
| I5 入口可用 | `AGENTS.md` 读完就知道怎么干活 | 不写日志、台账、进度；行数 ≤120 |

规则只有能从这五条推出来才写；推不出来的，不写。

## 三条反模式

- **拿手册当日志**：`AGENTS.md` 里挂批次、进度、待办。它每次对话整篇加载，越写越贵，最后没人读。
- **按类型分区**：`utils/`、`helpers/`、`common/` 什么都装，等于没有分区。按职责分：`src/`、`tests/`、`docs/`、`tools/`。
- **绕过脚本直接写盘**：`pce` 拦不住编辑器，只能事后 `check` 抓。所以“改完跑 check”必须写进入口文件。

## 边界

这个 skill 管“东西在哪、叫什么、引用得通不通”；不管代码质量、不管依赖与构建、不判断文档内容对不对。查不了的就说查不了，不假装能查。
