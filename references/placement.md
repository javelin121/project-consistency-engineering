# 新增、移动、改名、删除，各自怎么判断

四类动作，共用一条主干：**先查图，再查归属，出计划，确认，落盘，收尾**。区别只在中段。

## 新增文件

1. 它是什么：代码、测试、文档、数据、脚本。
2. 按 `navigation.md` 找候选目录；没有合适的，先问要不要新建目录或分区。
3. 名字按 `structure.yaml` 的 `naming`；没有约定就不猜，用你建议的名字并说明。
4. 出计划（建哪些、放哪、父表加不加行），确认后 `pce new`。一次可以建一批。

## 新增目录

1. 先查重：名字像不像已有目录、`what` 会不会跟已有分区撞。
2. 说明（“负责什么”）必须由人给，不能自己编。
3. 在父表加一行，同一个名字在两处出现要一致。
4. 目录一个个建；刚建的目录是叶子，先不建 `navigation.md`，等它有子目录时 `pce map` 会补。

## 移动

1. 先数引用：这个文件被谁链着、被谁 import 着。`pce check` 只能抓链接和带斜杠的路径，**点号 import 抓不到**，得自己扫。
2. 优先“旧位置留转寄条”：新位置建好，旧位置留一个转发文件，引用分批改，改完再删条。一次性 `git mv` 全搬是最容易出事的那种做法。
3. 改完跑 `check`，再跑项目自己的测试或至少 `import` 一遍。`check` 零 error 只证明结构自洽，不证明程序还能跑。

## 改名

同移动，另外多看一处：名字被写进 `AGENTS.md` 或导航文字里的地方。

## 删除

1. 先判断该不该归档：还要不要留凭据。要留就 `pce archive <路径> --reason "..."`。
2. 不要留就删，并在父表删掉那一行（`pce map` 会提示）。
3. 删完跑 `check`：还按旧路径引用的地方会以 S5/S6 报出来。

## 什么样算改完

四条全满足：

1. 文件已经落盘（或已删、已移）。
2. 受影响的 `navigation.md` 已更新。
3. `pce check` 没有新增 error。
4. 移动、改名、删除时，引用它的地方已经改完。

## 什么时候该拆目录

不看文件数，看信号：

- 你老想把东西放到“不太对但也能放”的地方。
- 一类东西改起来，总要连带改另一类。
- 有一批文件可以整批删掉或整批归档。

拆的时候按上面的“移动”走，别一次搬空。

## 大文件

不要进仓库。实在要进，先问一句“以后还会改吗”；会改的，放外部存储，仓库里只留指针。

## 预扩建（scaffold）

在写文件之前，先按项目定位把“家”安好：3–5 个分区，每个分区再往下拆一层，默认不超过 3 层。方案由 agent 给，`pce scaffold plan.yaml` 校验并落地（`--example` 看格式）。

拆的时候按“谁改它”分，不按“文件类型”分：`src/auth` 是一个模块，不是“放所有 .py 的地方”。每一层都要能一句话说清“什么该放进来、什么不该”。名字用英文 kebab，含义交给 `what`。

什么时候值得预扩建：项目刚起步、或者要插入一个新模块，结构还空着。什么时候不：文件还没想好怎么分工——先建目录只会得到一排空壳，S7 会一直提示它们空着（info，不拦你，但吵）。

空目录不进 git。clone 之后重跑一次 `pce scaffold` 就补齐；这是设计，不是缺陷。
